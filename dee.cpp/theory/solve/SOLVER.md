# SOLVER.md — the dee-serve capacity planner (Phase-7 component C)

Minimum-cost provisioning over the dee hierarchy, stated as a constrained optimisation and solved by enumeration over the discrete cell grid with closed-form memory sizing. Generated by `python -m theory.run_all solve` (deterministic, no RNG); code in `theory/solve/` (`model`, `pareto`, `surfaces`, `provisioning`, `report`).

## 0. The problem, stated

```
minimise    $/1k tok = 1000 * (r * replica_rate_s + volume_rate_s) / (lambda * L)
over        cell (discrete: constants.ALL_CELLS), host GiB (continuous, 17-point grid 4-1024), VRAM GiB (continuous within card memory, 4 fractions),
            prefetch budget {hints off, one measured legal hint budget}, batch policy b (grid), replicas r (integer, <= 4096)
subject to  Poisson arrivals lambda, request shape L (SERVE_ASSUMPTIONS: 512 decode tokens), per-stream decode SLO (5 / 20 / 50 tok/s),
            host/VRAM memory <= cell limits, storage bandwidth of the cell, rho <= 0.70 headroom (SOLVE_RHO_MAX) + batch-fillability,
            the exactness contract: a wrong prefetch hint may only waste bandwidth, never change execution
```

Named methods only: enumeration; Che's common-TTL residence model (THEORY.md 3.1) with the two-level miss-through form (5.1); the overlap-corrected token roofline `T_pred` (5.1); Little's law; an M/M/1 response-time inflation with a Kleinrock batch-fillability window; the batch-overlap correction `u_i(b) = 1-(1-pi_i)^b`. Every constant is tagged in [`../data/provenance.csv`](../data/provenance.csv).

**Every (model, lambda, SLO) combination is infeasible** — the per-stream decode SLO (>= 5 tok/s/stream) exceeds what any bounded cell delivers per stream: feasibility needs X/b >= slo/(1-rho), i.e. >= ~16.7 tok/s per stream at SLO=5, while b=1 per-replica rates top out at ~3-8 tok/s on the enumerated cells. Replication scales aggregate throughput but cannot raise a stream's own rate. dee-serve is a cost/throughput play at batch; it cannot promise per-stream decode speed at these SLOs — consistent with P15c's no-cell-wins-at-b=1.

## 4. Limitations (dominant ASSUMPTIONS)

1. `COMPUTE_EFF = 0.6` of vendor dense-tensor peak (range 0.3-0.8) and the anchor-calibrated per-touch cost `t_0 = 387 us` (FALSIFICATION assumptions 1 and 7) — no in-repo GPU microbenchmark (data needed).
2. **The dense-price ambiguity** above — unresolved, 3.57x, and it flips the break-even.
3. `SOLVE_CORES = 2` CPU cores per replica (ASSUMPTION 1-4) vs serving.py's full-cell billing — see the disagreement table.
4. Popularity-shape transfer (S_TRANSFER) for the non-DSv4 stores; the MiMo/MiniMax frontiers inherit DSv4-Flash's locality (data needed: per-model router traces).
5. The dense baseline's 200 tok/s achieved decode and the SOLVE_DENSE_SCALE throughput law (dense throughput does NOT fall with resident footprint) are deliberately conservative toward the competitor.
6. `rho_fill` batch-fillability (Kleinrock K >= b-1) is a modeling convention for continuous batching; no measured scheduler exists.
