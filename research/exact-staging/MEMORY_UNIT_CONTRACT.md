# MEMORY_UNIT_CONTRACT.md — the single memory-unit and safety-system definition

Branch: `research/exact-staging` · Date: 2026-09-04
Machine-readable mirror: `results/memory_frontier.json → unit_contract`
(generated by `recalibrate_model.py`; tests enforce consistency).

## 1. Why this contract exists

At `fcc8ca2`, `MEMORY_BUDGET.md`'s hand-typed table disagreed with
`results/memory_frontier.json` (10.0 GiB/GPU: 31.36 GB vs 29.23 GB projected
total; 0.64 GB vs 2.77 GB headroom). The JSON was internally consistent with
its printed formula; the markdown had silently folded the 2.0-unit safety
headroom into the totals with a stale conversion. Contract rules that make
that class of bug impossible:

1. **Machine-readable is the source of truth.** All projected-memory numbers
   are computed once in `recalibrate_model.py::memory_envelope()` and written
   to `results/memory_frontier.json`. Markdown tables are **generated** from
   that JSON between `<!-- BEGIN GENERATED:name -->` /
   `<!-- END GENERATED:name -->` sentinels.
2. **Every memory field carries its unit in its name.** Allowed suffixes:
   `_gib` (2^30 bytes), `_decimal_gb` (10^9 bytes), `_bytes` (raw).
   An unqualified `GB` field is banned; `tests/test_recalibration.py` lints
   every memory-related key in the emitted JSON and fails on violations.
3. **No silent system switching.** Both safety systems below are reported
   side-by-side per row; any single-number summary must name its system.

## 2. Units

| Unit | Meaning | Conversion |
|---|---|---|
| GiB | 2^30 bytes (what /proc/meminfo, VmHWM, and the engine report) | 1 GiB = 1.073741824 decimal GB |
| decimal GB | 10^9 bytes (what "32 GB class host" means colloquially) | 1 decimal GB = 0.9313226 GiB |
| bytes | raw byte counts (config knobs like `NATIVE_HOST_PACK_GPU0_BYTES`) | — |

## 3. Detected vs nominal host memory

- **Detected MemTotal (measured):** 31.35 GiB — `system_final_gib` in the
  memory digests, identical across all five seal runs on the Kaggle 2×T4
  host. This is the authoritative number for host-execution decisions.
- **Nominal host-class RAM:** "~32 GB" (decimal) — the project's thesis
  envelope for portable recommendations. 31.35 GiB = 33.66 decimal GB, i.e.
  the measured host is nominally a 32-GB-class machine whose usable
  MemTotal (31.35 GiB) sits *below* the nominal 32.0 decimal GB figure
  (29.80 GiB) once firmware/kernel reservations are subtracted at the
  factory. The strict contract is therefore the more conservative portable
  limit; the measured MemTotal is the more physically real one.

## 4. The two authoritative safety systems

Both are evaluated for every frontier row; each uses its own unit for its
own headroom (no cross-unit comparisons):

| System | Limit | Headroom field | Meaning |
|---|---|---|---|
| `MEASURED_HOST_MEMTOTAL` | 31.35 GiB (measured) | `headroom_gib_to_measured_memtotal` | Will this host survive the run? |
| `STRICT_32_DECIMAL_GB` | 32.0 decimal GB (thesis) | `headroom_decimal_gb_to_strict_contract` | Does this fit the portable envelope? |

Identity (by construction of the projection):
`headroom_gib_to_measured_memtotal` ≡ `projected_min_MemAvailable_gib`
(= MemTotal − projected_total). Both fields are reported; tests assert the
identity.

**Classification** (same gates in both systems, each in its own unit):
`SAFE_FOR_32GB` requires headroom ≥ 2.0 AND projected min-available ≥ 2.0 GiB
AND margin to the nearest clean OOM observation ≥ 2.0 GiB; failing exactly
one gate while fitting arithmetic → `BORDERLINE_FOR_32GB`; otherwise
`NOT_SAFE_FOR_32GB`. The row-level `classification` is the **conservative
intersection** (worst of the two systems) and is what recommendations use.

**Recommendation policy:** the largest budget that is SAFE under BOTH
systems. At the current evidence that is 10.0 GiB/GPU (cap 20 GiB total):
4.12 GiB / 2.77 decimal GB headroom, 7.68 GiB OOM margin.

## 5. Envelope terms (provenance)

| Term | Value | Kind |
|---|---|---|
| `measured_nonpack_hwm_gib` | 5.817 | MEASURED (max of 5 seal runs; range 5.60–5.82) |
| `system_rest_gib` | 0.91 | DERIVED (MemTotal − process HWM − min checkpoint avail) |
| `unmeasured_growth_allowance_gib` | 0.5 | UNKNOWN allowance (allocator/page-cache at larger pack; explicitly UNKNOWN, not measured) |
| pack | 2 × budget | DERIVED from the knob |
| OOM ledger | survived 25.74 / OOM 27.68 GiB pack total | MEASURED (v8/v9 campaign runs; v11 26.0 confounded by madvise thrash) |

Note the deliberately conservative shapes: non-pack uses the *max* observed
HWM; the growth allowance is added on top; the projection never credits the
min-checkpoint observation (7.76–7.97 GiB available at 16.983 GiB pack)
as free headroom.
